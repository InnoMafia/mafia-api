# Архитектура mafia-api

## Структура репозитория

```text
api/mafia/platform/v1/platform.proto
gen/go/mafia/platform/v1/
gen/openapi/mafia/platform/v1/platform.openapi.json
cmd/api/main.go
openapi.go
internal/
  handler/
    http.go
    http_test.go
    platform/
      service.go
      get_service_status.go
  usecase/
    get_service_status.go
  repository/
    database.go
```

| Путь | Что в нём находится |
| --- | --- |
| `api/` | Исходные Protobuf-контракты. Один `.proto` на сервис содержит RPC, сообщения запросов и ответов и HTTP-привязки `google.api.http`. |
| `gen/go/` | Go-типы Protobuf, gRPC-клиенты, серверные интерфейсы и HTTP/JSON-шлюз, сгенерированные Buf. |
| `gen/openapi/` | Сгенерированные документы OpenAPI 3.1. Пути следуют структуре Protobuf-пакетов в `api/`. |
| `cmd/api/main.go` | Точка входа. Читает конфигурацию, собирает зависимости, запускает HTTP- и gRPC-серверы и завершает их работу. |
| `openapi.go` | Встраивает сгенерированный OpenAPI в бинарник через `go:embed`. |
| `internal/` | Пакеты приложения с обработчиками, юзкейсами и репозиториями. |

## Слои

### Обработчики

`internal/handler/http.go` регистрирует gRPC-сервисы и HTTP-шлюз, а также
подключает служебные HTTP-маршруты, включая OpenAPI и Swagger UI.
Каждый Protobuf-сервис имеет свой пакет в `internal/handler/`. В папке сервиса
`service.go` содержит тип сервиса и его конструктор. Каждый RPC реализован в
отдельном Go-файле с именем метода в `snake_case`.

Обработчик преобразует запрос транспорта во входные данные юзкейса, вызывает
юзкейс и преобразует результат или ошибку в ответ транспорта.

### Юзкейсы

В `internal/usecase/` каждый юзкейс лежит в отдельном Go-файле. Юзкейс
определяет вход и результат операции и объявляет интерфейсы доступа к данным,
которые ему нужны. Он получает реализации этих интерфейсов через конструктор.

### Репозитории

В `internal/repository/` реализация доступа к данным каждой сущности лежит
в своём Go-файле внутри общего пакета. Репозитории выполняют запросы к
PostgreSQL и преобразуют строки базы в типы приложения. `database.go`
содержит общий пул подключений и операции открытия, проверки и закрытия пула.

## Зависимости и путь запроса

`cmd/api` создаёт репозитории, передаёт их юзкейсам и подключает юзкейсы к
обработчикам. Обработчики зависят от юзкейсов. Юзкейсы обращаются к данным
через собственные интерфейсы, а конкретные реализации подключает `cmd/api`.

```text
gRPC       → обработчик → юзкейс → интерфейс репозитория → PostgreSQL
HTTP/JSON  → grpc-gateway → тот же gRPC-обработчик
```

Вызов `GetServiceStatus` проходит через обработчик в
`internal/handler/platform/get_service_status.go` и юзкейс в
`internal/usecase/get_service_status.go`. Юзкейс вызывает
`StatusRepository.Ping`, который реализует `Database` из репозитория.

## Генерация и тесты

- `buf.yaml` задаёт расположение контрактов, а `buf.gen.yaml` — плагины и
  директории вывода. `make generate` обновляет результаты в `gen/`.
  Код, который дописывает разработчик, хранится в исходниках своего слоя.
- Go-тесты лежат рядом с проверяемым кодом в файлах `*_test.go`.
  `internal/handler/http_test.go` проверяет HTTP и нативный gRPC с подставной
  реализацией интерфейса репозитория.
- `make check` проверяет форматирование, запускает Go-тесты и собирает код.
  Workflow в `.github/workflows/ci.yml` дополнительно сверяет результат
  генерации с коммитом и собирает Docker-образ.
