# Развёртывание из нескольких репозиториев

## Решение для первой версии

Один сервер клуба, один Docker Compose, отдельный образ каждого приложения:

| Репозиторий | Артефакт | Ответственность |
| --- | --- | --- |
| `mafia-api` | Образ Go-сервиса | Правила, данные, HTTP API и WebSocket |
| `mafia-web` | Образ статического веб-сервера | Судейский интерфейс |
| `mafia-hud` | Образ статического веб-сервера | Оверлей OBS |
| `mafia-extension` | Пакет расширения | Выпускается отдельно, вне Compose |

Образы web/HUD и их сборки пока не созданы. Сейчас `deploy/compose.yaml`
запускает только API. Эта основа не заменяет работающий `mafia-old`.

В будущем Compose дополним web, HUD и Caddy для HTTPS. Разные репозитории
не требуют разных доменов. Один origin упрощает cookies, HTTP и WebSocket
и не требует широких CORS-разрешений.

Предлагаемое распределение маршрутов:

- `/api/*` и `/ws` → API;
- `/hud/*` → HUD;
- остальные пользовательские маршруты → web.

Эти игровые маршруты ещё не реализованы. При переносе существующих игр
потребуется сохранить старые пути, идентификаторы и ссылки доступа либо
добавить проверенный слой совместимости; новый prefix сам по себе этого не решает.
Frontend-образы должны обслуживать собственные ассеты и SPA-маршруты с
согласованным base path, а Caddy — корректно проксировать WebSocket.

## Сборка и выпуск

Каждый репозиторий отвечает за проверки и сборку своего образа.
Предлагаемое хранилище — GHCR:

```text
ghcr.io/innomafia/mafia-api
ghcr.io/innomafia/mafia-web
ghcr.io/innomafia/mafia-hud
```

Это целевые имена, а не уже опубликованные образы.
Текущий CI проверяет Go-код и собирает контейнер, но ничего не публикует.
Публикацию по release-тегам и доступ сервера к GHCR нужно настроить отдельно.

Правило для сервера: **скачивать готовые образы, не собирать несколько main**.
Не использовать `latest`, автоматический `git pull` или независимо обновляемые
контейнеры без проверки совместимости.

В `deploy/` будем хранить описание каждого проверенного релиза:

```text
API_IMAGE=ghcr.io/innomafia/mafia-api@sha256:<digest>
WEB_IMAGE=ghcr.io/innomafia/mafia-web@sha256:<digest>
HUD_IMAGE=ghcr.io/innomafia/mafia-hud@sha256:<digest>
CONTRACT_VERSION=<supported-version>
```

Это пример будущего release manifest, а не готовый файл окружения.
Он содержит только версии и может храниться в Git. Пароли и токены
должны оставаться в отдельном серверном окружении, вне репозитория.
Reverse proxy и другие инфраструктурные образы также следует фиксировать.

Контракты HTTP/WebSocket и исходники генерируемого TypeScript SDK будут жить
в API-репозитории. Web, HUD и расширение подключают конкретную версию SDK.
Разные приложения могут выпускаться независимо, пока их контракты совместимы.
Перед переключением проверяется весь выбранный набор образов.

## Что можно запустить сейчас

Из корня репозитория:

```sh
docker compose -f deploy/compose.yaml up -d --build
curl --fail --retry 10 --retry-connrefused --retry-delay 1 http://127.0.0.1:8080/readyz
docker compose -f deploy/compose.yaml logs api
docker compose -f deploy/compose.yaml down
```

Пример настройки:

```sh
test -f deploy/.env || install -m 600 deploy/.env.example deploy/.env
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --build
```

Не перезаписывайте уже настроенный `.env`. Без `--env-file` используются
окружение вызывающего процесса и значения по умолчанию в Compose.
Приложение самостоятельно `.env` не читает.
Для отдельно установленного Compose v2 команда `docker-compose` заменяет
`docker compose` во всех примерах.

Текущий runtime-образ не содержит shell/curl. Проверки `/healthz` и `/readyz`
выполняются с хоста или внешним мониторингом. У контейнера пока нет собственного
healthcheck: состояние `running` в Compose не доказывает готовность API.
Пока нет зависимостей, readiness означает только работоспособность HTTP.

## Обновление сервера после настройки публикации

1. Выбрать и проверить совместимый release manifest.
2. Скачать закреплённые образы через `docker compose pull`.
3. Проверить итоговый `docker compose config`; сохранить текущий manifest.
4. Переключить выбранные сервисы через `docker compose up -d --no-build`.
5. Проверить HTTP readiness, затем сценарий судья → API → HUD.

Пока игровой протокол не реализован, последний сценарий проверить нельзя.
После появления клиентов нужны также проверки переподключения, доступа по
ссылкам и схемы экспорта. Расширение не обновляется вместе с контейнерами:
нужно учитывать поддерживаемые им версии API.

Обычный Compose не гарантирует атомарное переключение нескольких сервисов.
Поэтому контракты должны допускать согласованное окно совместимости. Изменения,
которые его нарушают, требуют остановки записи и отдельного порядка миграции.
Kubernetes и распределённый релизный оркестратор для одной установки не нужны.

## Данные, остановка и откат

В текущей основе базы и пользовательских данных ещё нет. Когда появится
SQLite, нужен именованный том, отдельный пользовательский backup и проверка
восстановления. Не хранить данные внутри заменяемого образа.

Перед миграцией существующей установки:

1. Остановить все процессы, записывающие данные.
2. Сделать согласованную копию всего `DATA_DIR`, учитывая SQLite WAL.
3. Проверить восстановление копии и сохранить прежний набор образов.
4. Убедиться, что новый формат допускает согласованный способ отката.

Не запускать Node и Go на запись в один каталог данных.
Откат нужно испытать **после записей новым сервером**: восстановление только
старого backup потеряет последующие действия судьи. На период совместимости
новый сервер должен сохранять читаемый старым сервером формат; иначе нужен
отдельный план переноса новых изменений либо исправление текущей версии.

Время остановки контейнера должно превышать `SHUTDOWN_TIMEOUT`.
Сейчас по умолчанию это 15 и 10 секунд соответственно. После появления
WebSocket завершение долгоживущих подключений нужно реализовать и проверить
отдельно: обычный `http.Server.Shutdown` не закрывает hijacked connections.
